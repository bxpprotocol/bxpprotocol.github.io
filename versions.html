Versions, pinning, and citation

BXP v2.0 is a stable specification. This page explains how to pin a version so your integration or citation keeps resolving to the same document, and how to cite the work.

Why pinning matters A specification that can change without warning cannot be integrated against. BXP commits to semantic versioning: a breaking change means a new MAJOR version with 18 months advance notice, and MINOR additions are backward compatible by design. Pin to a MAJOR version and a minor release cannot invalidate your integration.

Pinning a version

WantUseMeans
mainhttps://github.com/bxpprotocol/bxp-spec/blob/main/SPEC.mdAlways the latest work. Fine for reading, not for integrating.
v2.0.../blob/v2.0/SPEC.mdThe specification as published. Stable, and what conformance is judged against.
<commit>.../blob/<sha>/SPEC.mdExactly one immutable state. Use this in a paper or a reproducibility record.
DOIdoi:10.5281/zenodo.18906812Archival, time-stamped, and resolvable forever. Preferred for citation.

For code dependencies, the equivalents are the bxp-sdk package version, or a git submodule pinned to a tag.

Pinning the API contract

The REST contract is committed as an OpenAPI 3.1 document, generated from the reference server so it cannot drift from the implementation:

openapi.json   canonical, machine-readable
openapi.yaml   same document, human-diffable

Pin one of these into your repository and diff it in CI. When it changes incompatibly, you find out in a pull request rather than in production.

Compatibility policy

ChangeVersion bumpYour integration
New optional fieldMINORKeeps working. Ignore fields you do not recognise.
New agent under extMINORKeeps working.
New endpointMINORKeeps working.
Field removed or retypedMAJORBreaks. 18 months advance notice before it ships.
Changed checksum or framingMAJORBreaks. The wire format is frozen within a major version.

Citing BXP

The specification and the reference implementation each have a permanent DOI. Cite the specification when referring to the format or the protocol; cite the implementation when referring to the software.

WhatDOI
Specification v2.0doi:10.5281/zenodo.18906812
Reference implementationdoi:10.5281/zenodo.18907003

Machine-readable citation metadata lives in CITATION.cff, so GitHub's “Cite this repository” and tools such as doi2bib resolve authors, title, and version without you maintaining a second copy.

What to cite carefully

If your work uses bxpHri, say plainly that the index is experimental and not clinically validated. Citing the specification for the data format and privacy model is straightforward; treating the composite index as a validated health metric would misrepresent the state of the work.
